# Kinds follow the forwarder

A resource's kind is fixed. It is the hash of the resource's logic ref and label ref, and the resource's commitment covers both. What is not fixed is the point the compliance circuit uses for that kind when it builds the delta — the kind base. The circuit takes it from the tree in force when the proof is made, and uses the kind itself when the tree has no entry for it. The delta check is per transaction. So assigning a kind a new kind base does not, by itself, make resources of that kind unusable: a transaction that consumes them balances as long as every resource in it uses the tree in force. Two things do go wrong, and they are the only rules.

**R1 — One forwarder.** Two kinds may share one kind base only if one forwarder holds the tokens behind both. Otherwise a token deposited under one kind can be withdrawn under another. This is the rule that protects funds, and it is why sharing a kind base is reviewed like a permission to create tokens.

**R2 — Exit.** A kind with unspent resources must always have a way out: the forwarder accepts its logic ref, so its resources unwrap; or its kind base equals that of a kind the forwarder accepts, so its resources convert first. This is the rule that keeps resources usable. It breaks when the forwarder has moved to a new logic ref and the entry that let the old resources convert is gone.

So a tree is a set of fungibility domains. A fungibility domain is one forwarder holding one token on one chain, and the kinds whose resources those tokens back. Every member is assigned the fungibility domain's kind base: the kind of the active circuit version under the label of the environment's forwarder. That member therefore keeps its own kind, and every other member is an alias of it. The members are the listed circuit versions under the label of the environment's forwarder, except a version that only the legacy ERC20 forwarders accept, and, on a migrated chain, the logic ref that the legacy ERC20 forwarder accepts under its own label, for each token that soft-migrates. No resource of a version carries the label of a forwarder that never accepted the version, so a member under that label would serve no resource. Generic call and padding have no fungibility domain: their resources are ephemeral, so nothing is ever made fungible with them. The generic call entry is assigned its own kind, so that the circuit reads its kind base instead of computing it. Padding is not listed: nothing converts padding resources and their speed does not matter, so the circuit computes their kind base. A padding entry would also make the trees depend on the arm-risc0 release, since the padding logic ref changes with each release. pa-evm pins arm-risc0 and loads these trees, so the repositories would depend on each other in a circle.

Which kind base a fungibility domain uses does not matter for safety: moving a whole fungibility domain to a new one only makes in-flight transactions re-prove. So the kind base follows the active version, the one the backend creates resources of. A release makes the new version active and the previous one deprecated, which moves every ERC20 kind base on every chain to the new version's kind and turns the previous version's entries into aliases. The active version keeps its own kind under the label of the environment's forwarder, so that it needs no tree to know its kind base; the deprecated versions and the members under the legacy forwarder's label are what the tree exists for. Exactly one version is active, and it is the highest listed: an older version never becomes active again, because the adapter denies the logic ref of a broken release and a higher release replaces it, and the backend can go back to creating an older version without any change to the tree.

The protocol adapter, not the tree, stops a broken circuit. The tree can only change what a circuit's resources are fungible with, and anyone can prove with a published circuit on their own machine. A version whose logic ref the adapter denies stays listed while resources of it can need their conversion. An entry is not free: each time the entry count passes a power of two, the tree gains a level, and every Merkle path a proof checks gets one more hash. So a version has members only under the labels of the forwarders that accept it or accepted it.

## The legacy ERC20 forwarder

On a chain that ran a legacy protocol adapter, the ERC20 forwarder changes once. The legacy ERC20 forwarder is immutable and fixes the legacy protocol adapter as its caller, so the protocol adapter needs a forwarder at a new address, and with it a new label. The environment's forwarder is an upgradeable proxy, so its address and its label stay across upgrades. The legacy ERC20 forwarders accept `bc1232…`, the circuit version 1.0.0. The environments' forwarders accept only the active version, so no resource of 1.0.0 carries their labels. `data/circuit-versions.json` keeps one line per logic ref and marks 1.0.0 with `legacy_forwarders_only`: the version has members only under the labels of the legacy forwarders, and only for the tokens that soft-migrate. A release of the crate that ships the circuit, such as transfer_library 2.0.0 or 3.0.0-rc.2, does not change its logic ref, so it is not a new version.

The forwarder repository records each legacy ERC20 forwarder with the logic ref it accepts, as pa-evm records the legacy protocol adapters. The generator reads that record through the forwarder bindings. Every tree of a chain that records both a legacy ERC20 forwarder and the environment's forwarder gets members under the legacy forwarder's label, one per token the supported-token list marks for soft migration. On a chain whose protocol adapter did not take the legacy state, they are harmless: resources created on a legacy protocol adapter reach a protocol adapter only through the state migration, so a legacy-forwarder resource there can only come from a conversion inside its fungibility domain. [ADR-0011](./0011-legacy-members-only-on-migrated-chains.md) limits these members to the migrated chains of each environment.

The members under the legacy forwarder's label enter the tree before the tokens move, and the order of the migration keeps R1. The tree is installed while the protocol adapter is paused, before the legacy protocol adapter stops. The legacy state is copied in, and the protocol adapter stays paused. The legacy forwarder's tokens move to the environment's forwarder, and only then does the protocol adapter unpause. A paused protocol adapter executes nothing, and the environment's forwarder pays out only on calls from its protocol adapter, so no legacy-forwarder resource can unwrap before its tokens have moved.

## Consequences

- `data/circuit-versions.json` is the one authored decision about circuits: the ERC20 circuit versions, each with its logic ref, its status, and whether only the legacy forwarders accept it (`legacy_forwarders_only`). A release appends the new version as active and sets the previous one to deprecated; the generator requires exactly one active version, the highest listed. The generator checks every version whose crate is pinned against the logic ref that crate compiles to, so raising a pin without listing the release fails the build.
- The active version under the label of the environment's forwarder keeps its own kind, so the circuit computes its kind base without the tree; every other member is an alias the tree must carry. An alias does not need an entry for the kind it names, since `anoma-rm-risc0` reads each `kind_base` from the tree (ADR-0004). So the active member has an entry only if `data/tokens.json` sets `precompute_kind_base` for its token: the circuit then checks a Merkle path to the point instead of computing it by hash to curve. Each time the entry count passes a power of two, the tree gains a level, and every Merkle path a proof checks gets one more hash. The tree grows with the aliases and the tokens that ask for the entry, not with twice the tokens.
- A member's `status` describes the entry, not its circuit version: `active` for the active version under the label of the environment's forwarder, `deprecated` for every other member, the members under the legacy forwarder's label included. So `status` is `active` if and only if `alias_of` is absent.
- The `token_entries_share_their_fungibility_domains_kind_base` test checks the embedded trees offline: an ERC20 or SPL token entry is assigned its fungibility domain's kind base, its `status` is `active` if and only if it has no `alias_of`, and every other entry is assigned its own kind. The `a_token_has_an_active_row_if_and_only_if_it_asks_for_a_precomputed_kind_base` test checks each token's flag against the trees.
- The generator requires the logic ref of each legacy ERC20 forwarder to be a listed version.
- The promotion gate reads the environment's ERC20 or SPL token forwarder on each chain and requires that the logic ref it accepts is listed and not marked `legacy_forwarders_only`. That is R2, checked on chain. The active version cannot be marked: it keeps its own kind under the label of the environment's forwarder. Solana has no legacy forwarder, so no SPL token version can be marked.
- A version keeps its members under the label of the environment's forwarder while that forwarder can hold resources of it. Nothing checks that `legacy_forwarders_only` is set only on a version that no environment's forwarder ever accepted, so review must.
- `data/tokens.json` says per token whether the legacy forwarder's label joins its fungibility domain, in `soft_migrate_from_legacy_forwarder`. A token set to `false`, or missing from the list, gets no member under the legacy forwarder's label, and its legacy-forwarder resources stay where they are. Where every legacy-forwarder resource must have an exit, every token the legacy forwarder wrapped has to be listed and set to `true`. Nothing checks this, so review must.
- A token whose balance in the legacy forwarder has not moved must have no member under the legacy forwarder's label when the protocol adapter unpauses. Its `soft_migrate_from_legacy_forwarder` stays `false` until the balance moves.
- pa-evm's migration run unpauses right after the copy-in. For this order it must stop before the unpause, and a second run unpauses after the legacy forwarder's tokens moved.
- After the legacy forwarder's tokens moved, the environment's forwarder of that protocol adapter is upgraded, never redeployed. A new forwarder would leave the moved tokens behind the old label while the members under the legacy forwarder's label take the new kind base, which breaks R1 and R2.
- Nothing checks that a listed version stays listed. A deleted line is the one edit review must catch, and `CODEOWNERS` routes it to a named person.
